# korvarix-llm — Open WebUI frontend (LLM panel)

Frontend-only Open WebUI deployment for korvarix.com's LLM panel. Runs on its
own machine; models arrive later from a separate LLM box via `OLLAMA_BASE_URL`.

## What this is (and isn't)

- **Is:** the Open WebUI web interface, auth on, signup closed, one local
  admin, bound to `127.0.0.1` only (a reverse proxy fronts it).
- **Isn't (yet):** model hosting — this box serves the UI only, so it uses the
  plain `:main` image (not `:ollama`/`:cuda`) and runs with zero models until
  the LLM machine is wired up.

## Install

> **Upload the whole `korvarix-llm` folder to the server** — `install.sh` alone
> is enough for the container, but the **gate** (`./install.sh gate`) also
> needs `Dockerfile.gate`, `gate/gate.js` and `lib/` next to the script.

```bash
cd korvarix-llm
./install.sh            # installs docker if missing, writes .env, starts the container
./install.sh gate       # builds + runs the SSO gate container (needs the full folder)
./install.sh nginx      # nginx reverse proxy: LLM_DOMAIN -> gate (+ Let's Encrypt)
./install.sh check      # strict verification: vhost loaded by nginx + upstream answering
./install.sh status
./install.sh logs 100
```

`install.sh` is idempotent — re-run it after editing `.env` to apply changes
(container is recreated, data volume survives). Every `install`/`update` also
re-verifies the proxy (config still loaded, upstream still answering) once
`./install.sh nginx` has been run at least once. `./install.sh nginx` itself
ends with the same verification and fails loudly if the vhost isn't live.

## nginx proxy

`./install.sh nginx` (as root) installs nginx + certbot if missing, writes the
vhost config, fetches the Let's Encrypt certificate (HTTP-01 via certbot
webroot), and installs a renewal deploy hook that reloads nginx.
Requirements: `LLM_DOMAIN` set in `.env`, its DNS pointing at this machine,
and port 80 reachable. The block proxies to `http://127.0.0.1:8210` with
websocket upgrade headers and long stream timeouts (LLM token streaming /
socket.io), following the same shape as the game-node proxy configs.

**Distro-agnostic:** the package install tries apt → dnf → yum → zypper →
pacman → apk, and the config/webroot locations are detected at runtime
(`nginx -V` conf-path, then `conf.d/*.conf` include vs Debian `sites-available`
+ symlink, webroot candidates `/var/www/html`, `/var/www`, `/srv/www`,
`/usr/share/nginx/html`). If the package install fails (e.g. EPEL missing on a
RHEL clone), install `nginx` + `certbot` manually and re-run — the script then
skips straight to config + cert.

| Variable | Default | Purpose |
|---|---|---|
| `LLM_DOMAIN` | empty | Public hostname, e.g. `llm.korvarix.com` |
| `LE_EMAIL` | `admin@korvarix.com` | Let's Encrypt notice address |

## Phase 2 (implemented): korvarix account gate + avatars

Access requires a korvarix.com account **with the LLM access package**
(admin-granted on request, Admin → Users → LLM). No self-serve purchase.

```
korvarix.com  ──"LLM Panel ↗"──▶  POST /api/sso/llm/request (package check)
                                        │  one-time code (sso_codes, audience llm)
                                        ▼
        llm.korvarix.com/sso/complete?code=…   (nginx → gate :8211)
                                        │  POST /api/sso/llm/redeem (shared LLM_SSO_KEY)
                                        ▼
        gate: session cookie + avatar sync ── trusted headers ──▶  open-webui :8210
```

**Direct visits are supported:** opening `llm.korvarix.com` without a panel
session bounces through `korvarix.com/account/llm-launch` — if that browser
holds a korvarix session, the SSO code is minted automatically (no button
click); if not, it flows through login and the launch continues by itself.

Flow, mirroring the ModDB SSO pattern:

1. **korvarix-base** mints a one-time code (`sso_codes` audience `llm`) and
   re-checks the package at redeem time (`POST /api/sso/llm/redeem`, shared
   `LLM_SSO_KEY`). The account menu shows "LLM Panel ↗" only when
   `/api/auth/llm-entitlement` says yes.
2. **The gate** (`gate/gate.js`, run `./install.sh gate`) redeems the code,
   sets a signed session cookie, and proxies everything to Open WebUI with
   the trusted headers (`X-Korvarix-Email` / `X-Korvarix-Name`) — Open WebUI
   auto-provisions the matching account on first sign-in. Sign-outs clear the
   gate cookie too. Requests without a session bounce to korvarix.com/login.
3. **Avatars (gravatar removed):** on every sign-in the gate syncs the
   korvarix avatar into the Open WebUI profile using an **OWUI API key**
   (`OPEN_WEBUI_API_KEY`, minted by the admin in Open WebUI: Settings →
   Account → API Keys — no password auth anywhere) — either as the korvarix
   CDN URL (302-forward, default) or a data-URI. Provisioned users never show
   gravatar; accounts without an avatar get Open WebUI's initials fallback.
4. **Admin grant:** Admin → Users → "LLM" button → grant/revoke. Revocation
   blocks the next sign-in (redeem-time check); active sessions age out via
   the gate cookie TTL (`GATE_SESSION_TTL_S`, default 7 days).

Setup order on the LLM box (order matters — `gate` before `nginx`):

```bash
./install.sh            # open-webui container (loopback :8210)
./install.sh gate       # builds + runs the gate container (loopback :8211, docker net to open-webui)
./install.sh nginx      # llm.korvarix.com -> gate -> open-webui
# then: copy LLM_SSO_KEY from korvarix-llm/.env into korvarix-base/.env,
#       create an OWUI API key (admin: Settings -> Account -> API Keys) and
#       paste it as OPEN_WEBUI_API_KEY in korvarix-llm/.env, re-run install.sh
```

The gate runs as a second Docker container (no host Node.js needed) on a
`korvarix-llm-net` network with the alias `open-webui` for the UI container —
the gate reaches it over the bridge, never over the host loopback. Running
`gate` after `nginx` automatically repoints the existing vhost at the gate
(so an nginx-first setup can never bypass SSO).

> The trusted headers must never be reachable except through the gate —
> Open WebUI stays on loopback, nginx terminates TLS and forwards only to the
> gate, and the gate strips any inbound `X-Korvarix-*` headers from clients.
